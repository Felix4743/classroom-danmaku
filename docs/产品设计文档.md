## 1. 项目背景

大学课堂最普遍的问题不是老师讲得不好，而是**反馈断层**：

- 老师讲完一章问「听懂了吗」，台下没人回答——但实际没听懂的人可能占一半。
- 想提问的学生要承担三重成本：举手被围观的社交压力、打断课堂节奏的心理负担、以及「这么简单都不会」的自我审查。
- 老师拿到的反馈永远是滞后的（期中评教、期末成绩单），**已经来不及调整讲课节奏**。
- 真正有价值的信号往往不是「我不懂」，而是「这里卡住了 ×23」这种**群体性**信号，而它在传统课堂里根本无法被采集。

**本项目要解决的核心问题：**

> 课堂中学生的真实反馈，无法被低成本地采集、聚合和实时呈现。

弹幕是这个问题的解法，不是目的。它同时提供三种能力：**低门槛表达**（打字比举手容易）、**匿名安全感**（去掉社交压力）、**群体信号聚合**（23 个人同时卡住，屏幕上一眼可见）。

### 1.1 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 在线教学平台（课件/作业/考试） | 与核心问题无关，且已有成熟产品<br>（注：若采纳 Q-007 路线 C，此边界会部分移动） |
| 课堂考勤 | 会让学生把弹幕系统和「被监控」绑定，直接摧毁发言意愿 |
| 录播与回放 | 技术复杂度高，且不是活跃课堂的手段 |
| 社交功能（私信、关注、好友） | 课堂只需要 90 分钟的临时场域 |

## 2. 设计前提：四个本质矛盾

这一章是整个设计的立论基础。后面所有的功能设计，都是在回答这里的四个问题。

### 2.1 弹幕提供的是「氛围」，课堂需要的是「信息」

B 站弹幕能成立，依赖三个前提，而课堂**一个都不具备**：

| | B 站 | 课堂 |
|---|---|---|
| 观众注意力 | 全在视频内容上，弹幕是叠加的情绪层 | 老师要对着**同一块屏幕**讲课，弹幕直接与讲课内容争抢注意力 |
| 内容可回看 | 能暂停、能关弹幕、能重看 | 一次性的，错过就没了 |
| 弹幕的信息价值 | 极低也没关系（「哈哈哈」「233」「前方高能」） | 低价值弹幕 = 纯噪音，会淹没有效信号 |

B 站弹幕里绝大多数是**情绪表达**而非**信息**，它的作用是让观众感到「有很多人跟我一起在看」。这个价值平移到课堂里，叫**破冰**——让不敢举手的学生第一次有了发声渠道。这是真实价值，但它**有保质期**，新鲜感大约 2~3 周。

**设计结论：** 「全屏飘过」保留，但定位为**互动模式**，而不是课堂的默认形态。

- **全屏飘过** → 用于互动时刻：老师抛出问题、开启讨论、破冰环节
- **侧边条带** → 用于正常讲课，不遮挡课件
- 两者由老师一键切换，**默认关闭**

> 全屏模式必须配一个「一键清屏 / 暂停」的开关，且不能有二次确认弹窗。第一次出现刷屏而老师来不及制止，他就再也不会开第二次了。

### 2.2 老师是唯一的信息瓶颈

一个 90 人的班级，一节课产生 200 条弹幕是常态。老师**读不完**，这是物理限制。

由此推出本产品的第一性命题：

> **学生发的弹幕如果没有被回应，他第二次就不会再发了。**

反馈闭环不闭合，弹幕墙就只是个会动的装饰品。所以产品的重心**不是「怎么把弹幕飘出来」，而是「怎么让老师在一秒内看到最重要的 5 条」**。

三个解决机制：

1. **聚合计数** —— 学生不是发一条「没听懂」，而是点一个「没听懂」按钮；屏幕上那一条显示为 `没听懂 ×23`。学生看到自己的参与产生了可见效果，老师一眼看到重点。它比让 23 个人刷 23 条重复弹幕强一个量级，而且**天然抗刷屏**。
2. **点赞顶上来** —— 让好问题冒头。注意：点赞排序（要「固定」）和实时滚动（要「流动」）本质冲突，所以不能把高赞弹幕直接扔回弹幕流，必须给它**独立的展示位**。
3. **待回应问题池** —— 老师需要一块比弹幕墙更小的面板，只放「需要我回应的东西」。

### 2.3 匿名与秩序

这是最影响产品气质的决定。

| 方案 | 效果 | 代价 |
|---|---|---|
| 完全匿名 | 活跃度最高 | 一条不当言论就能让整门课被叫停，老师**没有任何反制手段** |
| 完全实名 | 秩序最好 | 学生不敢问「这么简单都不会」的问题，而**恰恰是这些问题最有价值**，活跃度大幅下降 |
| **对同学匿名 + 对老师可追溯** | 兼顾 | 需要一套身份采集流程（见 §8.6） |

**已采纳：对同学匿名、对老师可追溯。**

机制上等同于「匿名评教但教务后台留痕」：威慑力存在，学生的心理负担消失。学生知道自己说什么老师最终能看到，但不知道具体哪条被谁看到——**这个「知道」本身就是秩序的来源**。

### 2.4 弹幕与课件争夺同一块屏幕 ⚠️

教室投影是**整屏镜像**（复制模式），这带来一个无法用 UI 技巧绕开的事实：

> 弹幕墙和课件是**互斥**的。全屏显示弹幕就看不到 PPT，切回 PPT 弹幕就消失。

而老师不可能在讲课时反复 `Alt+Tab`——每次切窗，全班都看得见；而且切走的那几十秒里弹幕全丢了。

**这不是细节，它决定产品形态。** 三条出路：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 窗口切换** | 弹幕墙做成独立页面，老师手动切 | 零开发成本 | 弹幕断续；切窗动作全班可见；老师要频繁操作 |
| **B 悬浮弹幕层** | 透明置顶、鼠标可穿透的浮窗，浮在 PPT 之上 | 体验最好，课件与弹幕兼得 | 需要安装客户端程序；教室电脑若有还原卡则每节课都要重装（可放 U 盘运行缓解） |
| **C 课件托管** | 老师提前上传课件，系统全屏播放课件并叠加弹幕 | 零安装；顺带支持学生端同步看课件 | 老师多一步上传操作；复杂动画课件转换会失真 |

**路线 C 的额外增值**（值得单独强调）：弹幕可以绑定到**具体哪一页课件**，老师能看到「第 12 页有 23 条没听懂」——这是精准到知识点的教学反馈，比一堆散弹幕有用一个量级。课后导出也变成「每页课件 + 该页的学生反馈」。

> 三条路线尚未选择，见 §6 的 Q-007。这是当前**最大的产品分叉**。

## 3. 目标用户与使用场景

### 3.1 角色

| 角色 | 说明 | 使用设备 |
|---|---|---|
| **主讲老师** | 核心用户。控制课堂、查看反馈、回应问题 | **自己的手机**（控制台）+ 教室电脑（只负责投影） |
| **学生** | 主要参与者。发弹幕、点赞、看回应 | 自己的手机 |
| **助教**（暂不支持） | 后续可承担问题池的初筛 | — |

> 产品成败的判据是**老师**：他愿不愿意在第二节课继续打开它。学生的新鲜感会衰减，但老师只要觉得「有用」，这件事就能持续。

### 3.2 典型场景

一节 90 分钟的大学专业课，阶梯教室，80 名学生。老师**不带电脑**，使用教室公用电脑，投影为整屏镜像。

- **00:00** 老师在教室电脑上打开浏览器、F11 全屏，显示弹幕墙与二维码；自己在手机上打开控制台
- **00:05** 学生扫码进入，填写身份（仅老师可见）+ 昵称
- **00:05** 开始讲课，弹幕墙处于**侧边模式**，偶尔飘过几条；老师手机静音放在讲台上
- **00:25** 讲到难点，老师掏出手机点「全屏模式」并抛出一个问题；弹幕瞬间刷起来，投影上全班都看得到
- **00:28** 老师手机震动——`这里没听懂 ×31` 达到阈值被推入待回应池；老师扫一眼，决定重讲一遍
- **00:35** 手机点「切回侧栏」，继续讲课
- **00:80** 老师打开问题池，把三条高赞问题置顶回应
- **00:90** 下课，导出本节课的弹幕记录

**这段场景暴露的关键约束**：老师全程**低头看手机**。这本身是个体验问题，必须在 §7.3 专门设计。

## 4. 设计原则

1. **老师的控制权 > 学生的表达自由。** 清屏、暂停、删除都必须一步到位，不允许出现确认弹窗拖慢反应速度。
2. **默认安静，需要时才热闹。** 全屏弹幕默认关闭，避免持续与课件争抢注意力。
3. **反馈必须闭环。** 任何一条被聚合或被点赞的弹幕，学生端都要能看见「我的声音起作用了」。
4. **零安装、零注册。** 扫码即用，不装 App、不登录、不填表单超过一层。**这条现在也适用于老师**：教室电脑上不能要求安装任何东西。
5. **身份信息永不上投影。** 投影是全班共享的，任何能追溯到具体学生的信息都只能出现在老师的手机上。

### 关于 Q-003 的说明（用户倾向「只做自由打字」，此处保留异议）

学生的实际输入成本对比：

- 自由打字：掏出手机 → 解锁 → 打开浏览器 → 聚焦输入框 → 打字 → 发送，**平均 15 秒**
- 预置按钮：掏出手机 → 点一下，**不到 1 秒**

差距是数量级的。更关键的是，**「聚合计数」机制完全依赖预置按钮**——没有按钮，就无法把 23 个人的意见合并成 `×23`，而只能得到 23 条重复弹幕，老师的瓶颈问题会更严重。

> 该决策标记为**待验证**。建议在 V0 原型阶段做一个 A/B 对照：同一批人，分别用「只有输入框」和「输入框 + 4 个快捷按钮」各发一轮，对比参与人数。用数据决定，不用直觉。

### 关于 Q-008 的说明（需实地确认，建议列成清单去教室跑一趟）

| 要确认的事 | 为什么重要 |
|---|---|
| 教室电脑能否上网 | 不能联网 → 公网方案直接失效，必须回到局域网，且服务只能跑在教室电脑上 |
| 投影是复制模式还是扩展模式 | 若是扩展模式，老师端可以放在讲台那块屏上，不必全程低头看手机 |
| 有无还原卡 / 管理员权限 | 决定「教室电脑零安装」这条约束是硬性的还是可以放宽 |
| 常见的浏览器版本 | 决定前端能用的 JS 特性（避免用了旧版不支持的语法） |

## 7. 功能设计

### 7.1 页面与角色划分

| 路由 | 页面 | 使用者 | 说明 |
|---|---|---|---|
| `/host` | 老师控制台（**手机端优先设计**） | 老师手机 | 弹幕墙 + 问题池 + 全局控制。**绝不上投影** |
| `/screen` | 大屏弹幕墙 | 投影 | 纯展示，无控制元素，全屏；**绝不出现任何身份信息** |
| `/m` | 学生端 | 学生手机 | 扫码进入 |

> `/host` 与 `/screen` 拆成两个页面，是 D-009 的直接要求：投影只放弹幕墙给学生看，老师用手机看控制台。**两者是同一个班的两条独立视图流，服务端按角色分流广播。**

### 7.2 学生端

**加入流程**（唯一一次表单，不超过一层）：

```
扫码 → 填写身份（学号 + 姓名，仅老师可见）
     → 填写昵称（可留空 = 「匿名同学」）
     → 进入
```

**主界面**：

- 顶部：当前课堂状态（「弹幕已暂停」/「进行中」）
- 中部：自己发过的弹幕及其实时状态（被点赞数、是否被老师置顶/回应）
- 底部：输入框 + 发送按钮（+ 快捷按钮，取决于 Q-003）
- 冷却中：发送按钮显示倒计时，避免无效点击

**关键交互**：发送后**本地先回显**，不等服务端确认，让手感即时；服务端确认失败（被限流/被拦截）时再撤销并给出原因。

### 7.3 老师端（`/host`，手机端）

**要正视的问题**：老师一边讲课一边低头看手机，观感差且分心。所以手机端**不能做成一个完整控制台**，定位应该是：

> **默认是「提醒器」，需要时才展开成「控制台」。**

**形态一：提醒器（默认，90% 的时间）**

- 一个大徽章：`3 个待回应`
- 达到阈值时**震动**提醒（`没听懂 ×31` 冲进问题池）
- 不做任何其他 UI，老师不用看它

**形态二：控制台（点开后）**

```
┌─────────────────────────┐
│ 待回应                  │
│ ▸ 这里没听懂 ×31        │
│   👍12  [置顶] [已回应] │
│ ▸ 能举个例子吗 ×8       │
│   👍7   [置顶] [已回应] │
├─────────────────────────┤
│  [ 清屏 ]   [ 暂停 ]    │   ← 大按钮，单手可点
│  [全屏模式] [侧栏模式]  │
├─────────────────────────┤
│ 在线 78 · 弹幕 213 · 41人│
│ ⚙ 屏蔽词 / 导出 / 设置   │   ← 折叠到二级页
└─────────────────────────┘
```

**手机端设计约束**：

- 只保留 4 个高频动作做成大按钮（清屏 / 暂停 / 置顶 / 删除），其余折叠
- 删除操作支持**左滑**，不做二次确认弹窗
- 所有操作必须在投影上 1 秒内生效
- 竖屏单手可操作，按钮最小高度 44px

**老师专属信息（只在这里出现）**：每条弹幕可展开查看发送者学号姓名，用于追溯；问题池支持「拉黑该设备」。

### 7.4 大屏弹幕墙（`/screen`）

- Canvas 渲染，全屏无边框
- 两种模式：**全屏飘过**（弹幕从右向左横穿整屏）/ **侧边条带**（底部 20% 高度区域内滚动）
- **置顶弹幕固定显示在顶部**，不参与滚动
- 被老师回应的弹幕，显示一个高亮描边
- 右下角常驻二维码，方便迟到学生扫码进入
- **安全红线：任何能追溯到具体学生的信息都不得出现在此页面**

## 8. 关键机制设计

### 8.1 弹幕渲染与轨道分配

Canvas 单画布，一帧一绘制。核心是把屏幕纵向切成 N 条**轨道（lane）**，新弹幕要找到一条不会追尾的轨道：

```
屏幕高度 H，弹幕行高 h → 轨道数 N = floor(H / h)

新弹幕到达时，按顺序尝试轨道 i = 0..N-1：
  若轨道 i 为空 → 占用
  否则检查该轨道最后一条弹幕 t：
    若 t 的右边缘 + 安全间距 < 屏幕右边界（即 t 已完全进入屏幕）
      且 新弹幕到达左边界所需时间 < t 移出右边界所需时间（不会被追上）
      → 占用轨道 i
  所有轨道都不满足 → 进入等待队列

速度策略：速度与弹幕长度正相关（长弹幕快一些），保证同屏停留时间一致
```

需要调优的手感参数（**全部做成老师端可调滑块**）：滚动速度、字号、透明度、同屏最大密度。

> 手感是这个产品最容易被低估的环节。飘得太快看不懂、太慢会积压；字号太大挡课件、太小后排看不见；透明度不够显脏、太高看不清。**这些参数只能在真实投影上反复调**，所以 V0 阶段就要把它们做成可调项，投入回报率极高。

### 8.2 聚合计数

在时间窗口（建议 30 秒）内，把语义相同的预置弹幕合并为同一条，计数累加：

- `没听懂 ×23` —— 学生点击后，屏幕上已存在的那条数字实时 +1，并有一个轻微放大的动效
- 窗口过期后，该条固定下来，不再增长

> 这是 **Q-003 依赖预置按钮**的根本原因：没有预置语义，就没有聚合的锚点。

### 8.3 点赞与热点

- 每个设备对同一条弹幕只能点一次赞（设备级去重）
- 点赞数不直接改变弹幕在流中的位置（会与滚动逻辑冲突），而是提升它在**问题池**中的排序
- 点赞数达到阈值时，弹幕墙顶部出现一条不滚动的「热点」提示

### 8.4 限流与防刷屏

服务端令牌桶，设备维度：

| 规则 | 阈值 |
|---|---|
| 发送间隔 | ≥ 3 秒 |
| 每分钟上限 | 10 条 |
| 单节课上限 | 200 条 |
| 连续触发限流 | 自动静默 60 秒，并提示学生 |

限流提示必须是**友好**的（「说得太快啦，3 秒后再来」），不是报错，否则学生会以为程序坏了。

### 8.5 内容安全

三层防护，按实际有效性排序：

1. **服务端限流**（§8.4）—— 最有效，直接掐断刷屏
2. **服务端屏蔽词** —— 命中即拦截，并对该设备计数
3. **老师一键撤回 + 拉黑设备** —— 兜底。屏蔽词永远做不全，真正的兜底是老师的手速

> 屏蔽词库不追求完备。真实课堂上，起决定作用的是「老师能在 2 秒内把那条删掉」。

### 8.6 身份与追溯机制

**问题**：如果学生完全匿名进入，老师端能看到的只有设备指纹（localStorage），而设备无法对应到具体的人——「可追溯」就名存实亡。

**方案**：首次进入时**必须填学号 + 姓名**，但：

- 学生之间看到的一律是「匿名同学」（或自取昵称）
- 只有老师端能展开查看真实身份
- 学生端**明确告知**「老师可以看到你是谁」

这个「告知」不是妥协，而是**有意为之的威慑设计**：学生知道自己说的话老师最终能看到，但不知道具体哪条会被翻出来——这正是秩序的来源，与匿名评教机制同构。

> **D-009 让这个机制变得更干净了**：老师端在手机上，身份信息天然不可能出现在投影上。若老师端在教室电脑屏幕上，则每次查看身份都要担心投屏泄露。

## 9. 技术架构

### 9.1 架构

```
              公网服务器（教室之外）
   ┌──────────────────────────────────────┐
   │  Node 进程                            │
   │   ├ 静态页面托管 (/host /screen /m)   │
   │   ├ WebSocket 服务                    │
   │   │   ├ 广播器（按角色分流）           │
   │   │   ├ 限流器（设备级令牌桶）         │
   │   │   ├ 屏蔽词过滤                    │
   │   │   └ 聚合器（时间窗合并计数）       │
   │   └ 存储：内存态 + 定时落盘            │
   └──────────────────────────────────────┘
        │                    │
   老师手机 /host       学生手机 /m ×N
   （控制台·私有）      （发弹幕）
        │
   教室电脑 /screen  ← 浏览器全屏，零安装
   （投影·全班可见）
```

**两条视图流的隔离是这个架构的关键**：

| 流 | 内容 | 可见范围 |
|---|---|---|
| `/screen` 流 | 弹幕内容、聚合计数、置顶状态 | 全班 |
| `/host` 流 | 上述全部 **+ 身份信息 + 问题池 + 控制状态** | 仅老师 |

服务端按连接角色分流广播，**身份信息永远不会进入 `/screen` 流**——这是服务端的责任，不能只靠前端不渲染。

### 9.2 选型

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js | 已装 v24.9.0；单进程足够，无需数据库 |
| 通信 | `socket.io` | 手机在教室切后台/信号抖动是常态，自带重连与房间 |
| 渲染 | 原生 Canvas 2D | 无框架开销，60fps 可控 |
| 前端框架 | **不用**（原生 JS） | 三个页面都很轻；且教室电脑浏览器版本不可控，少一层构建少一层风险 |
| 存储 | 内存 + JSON/SQLite 落盘 | 单节课数据量极小（≤500 条 × ~100B ≈ 50KB） |
| 二维码 | 服务端生成 | 需根据部署域名生成固定链接 |
| 托管 | 云服务器（1 核 1G 即可） | 见 Q-009 |

### 9.3 WebSocket 事件协议（草案）

| 方向 | 事件 | 载荷 | 说明 |
|---|---|---|---|
| C→S | `join` | `{ role, classId, identity?, nickname }` | 学生/老师/大屏加入 |
| C→S | `danmaku:send` | `{ text }` | 发弹幕 |
| C→S | `danmaku:like` | `{ id }` | 点赞 |
| S→C | `joined` | `{ deviceId, myHistory[] }` | 加入成功，回带历史 |
| S→C | `danmaku:new` | `{ id, text, nickname, color, ts }` | 新弹幕广播 |
| S→C | `danmaku:update` | `{ id, likes?, aggregate? }` | 计数变更 |
| S→C | `danmaku:remove` | `{ id, reason }` | 删除（老师撤回/屏蔽词） |
| S→C | `danmaku:pin` | `{ id, pinned }` | 置顶 |
| S→C | `state` | `{ paused, mode, online }` | 课堂状态同步（重连后必发） |
| S→C | `host:alert` | `{ id, reason, aggregate }` | **仅发给老师**：有新问题进入待回应池，触发手机震动 |
| C→S | `host:*` | — | 老师控制指令（清屏/暂停/删除/拉黑） |

> **重连后必须全量同步状态**，否则学生手机会停留在旧状态（比如老师已经清屏了，学生端还显示着旧弹幕）。老师手机锁屏后重开也属于这一类。

## 10. 教室环境约束与网络

### 10.1 教室硬件与软件约束（来自真实使用环境）⚠️

三条硬约束：

1. **投影是整屏镜像**（复制模式），投影上显示什么，学生就看到什么 —— 老师端不能上屏
2. **老师不带自己的电脑**，使用教室公用电脑
3. **教室电脑的软件环境不可控** —— 还原卡、无管理员权限、每节课重置是常态

由此推出四个结论：

| 结论 | 依据 |
|---|---|
| 老师端载体 = 老师自己的手机（D-009） | 约束 1 |
| 服务**不宜**跑在教室电脑上（D-011） | 约束 3：还原卡重启即清零，且可能无权限安装 Node |
| 教室电脑退化为「哑终端」（D-010） | 只需浏览器打开一个 URL 全屏显示，零安装、无残留 |
| 学生访问必须走教室之外 | 顺带消除 AP 隔离问题（§10.2） |

> **失效条件**：若教室电脑无法联网，以上结论全部推翻，必须回到局域网方案。此时服务只能跑在教室电脑上，需要确认它能否运行**免安装的绿色版 Node**，以及还原卡是否会在课间清掉它。→ 见 Q-008。

### 10.2 AP 隔离

**这是本项目在局域网方案下最容易翻车、且开发阶段完全发现不了的地方。**

学校 / 公共 WiFi 的 AP 经常开启**客户端隔离（AP Isolation）**，同一 WiFi 下的设备之间无法互相访问。表现是：

> 你在自己电脑上开两个浏览器窗口测试，一切正常；到了教室，学生手机根本连不上老师的电脑。

| 方案 | 到达率 | 代价 |
|---|---|---|
| 学生连校园网 → 访问教室电脑 | **可能完全不通** | 无 |
| 教室电脑开热点，学生连热点 | 高 | 学生需断开自己的网络；教室电脑需支持热点 |
| **服务部署到公网服务器** | **100%** | 需要服务器与域名，需处理并发与备案 |
| 教室电脑 + 内网穿透 | 高 | 需要额外配置，配置错误时老师无法自救 |

### 10.3 结论：公网方案在多重约束下胜出

结合 §10.1 与 §10.2，**公网托管**同时满足三条硬约束：

| 要求 | 公网方案是否满足 |
|---|---|
| 教室电脑零安装 | ✅ 只需浏览器 |
| 不受 AP 隔离影响 | ✅ 学生走 4G/5G 或校园网均可 |
| 老师端不上投影 | ✅ `/host` 在老师手机上 |
| 还原卡不影响 | ✅ 服务不在教室电脑上 |

> **成本**：一台 1 核 1G 的云服务器约 ¥100/年，学生机更便宜。域名另计。这是本项目唯一的持续性成本。
>
> **HTTPS**：弹幕不需要麦克风/摄像头，HTTP 够用。但部分校园网只放行 80/443 端口，建议配域名 + 免费证书（Let's Encrypt），避免用非标准端口。

## 11. 版本路线图

| 阶段 | 交付内容 | 验证的核心假设 |
|---|---|---|
| **V0** | 单机原型：一个页面自己给自己发弹幕；滑杆可调速度/字号/透明度/密度 | 弹幕的**手感**——这是所有体验的基础 |
| **V1** | 真多端：学生扫码发、投影飘、老师手机控 | ① 教室电脑能否联网并全屏显示 ② 手机控制链路是否顺手 ③ 端到端延迟 |
| **V2** | 老师管控：清屏、暂停、删单条、屏蔽词、限流、模式切换 | 老师愿不愿意开第二次 |
| **V3** | 互动：聚合计数、点赞、热点区、问题池、置顶、手机震动提醒 | 学生第 3 次课还发不发 |
| **V4** | 数据沉淀：课后导出弹幕记录、高频问题汇总 | 对老师有没有长期价值 |

**V0 必须先做的理由**：手感参数无法靠推理确定，只能在真实投影上试。如果 V0 跳过、直接做完整功能，最后很可能发现「氛围对了，但没人看得清」——那时返工成本极高。

**V1 之前必须完成 Q-008 的实地确认**，否则整个架构可能建立在错误前提上。

## 12. 验收标准（草案）

| 阶段 | 指标 | 阈值 |
|---|---|---|
| V0 | 弹幕渲染帧率 | ≥ 55 fps @ 同屏 100 条 |

| V3 | 聚合计数 | 时间窗内同语义弹幕正确合并 |
| V3 | 手机震动提醒 | 聚合数达阈值时触发，不误报 |

## 13. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| **新鲜感衰减**（最大风险） | 第 3 周后无人发弹幕 | 让弹幕与课堂内容强绑定（老师提问 → 弹幕作答），而不是让弹幕孤立存在 |
| **老师不适应手机操作** | 老师觉得麻烦，第二节课不再打开 | 提醒器模式：默认不打扰，只在阈值触发时震动；高频动作做成大按钮 |
| **教室电脑不能联网** | 公网方案失效 | Q-008 提前实地确认；预留绿色版 Node + 局域网备用方案 |
| **弹幕墙与课件互斥** | 老师上课要反复切窗 | Q-007 需做出选择；路线 B/C 各有代价 |
| **老师低头看手机的观感** | 学生觉得老师不专心 | 提醒器模式把手机使用时长压到最低 |
| **学生用弹幕聊天** | 弹幕流变成闲聊区 | 限流 + 老师撤回 + 屏蔽词 |
| **弹幕遮挡课件** | 影响正常讲课 | 默认侧边模式；全屏模式需老师主动开启 |
| **手机电量/流量** | 学生不愿长时间开着 | WebSocket 心跳降到最低；页面极简 |
