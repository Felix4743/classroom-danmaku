## 1. 项目背景

大学课堂最普遍的问题不是老师讲得不好，而是**反馈断层**：

- 老师讲完一章问「听懂了吗」，台下没人回答——但实际没听懂的人可能占一半。
- 想提问的学生要承担三重成本：举手被围观的社交压力、打断课堂节奏的心理负担、以及「这么简单都不会」的自我审查。
- 老师拿到的反馈永远是滞后的（期中评教、期末成绩单），**已经来不及调整讲课节奏**。
- 真正有价值的信号往往不是「我不懂」，而是「这里卡住了 ×23」这种**群体性**信号，而它在传统课堂里根本无法被采集。

**本项目要解决的核心问题：**

> 课堂中学生的真实反馈，无法被低成本地采集、聚合和实时呈现。

弹幕是这个问题的解法，不是目的。它同时提供三种能力：**低门槛表达**（打字比举手容易）、**匿名安全感**（去掉社交压力）、**群体信号聚合**（23 个人同时卡住，屏幕上一眼可见）。

### 1.1 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 在线教学平台（课件/作业/考试） | 与核心问题无关，且已有成熟产品<br>（注：若采纳 Q-007 路线 C，此边界会部分移动） |
| 课堂考勤 | 会让学生把弹幕系统和「被监控」绑定，直接摧毁发言意愿 |
| 录播与回放 | 技术复杂度高，且不是活跃课堂的手段 |
| 社交功能（私信、关注、好友） | 课堂只需要 90 分钟的临时场域 |

## 2. 设计前提：四个本质矛盾

这一章是整个设计的立论基础。后面所有的功能设计，都是在回答这里的四个问题。

### 2.1 弹幕提供的是「氛围」，课堂需要的是「信息」

B 站弹幕能成立，依赖三个前提，而课堂**一个都不具备**：

| | B 站 | 课堂 |
|---|---|---|
| 观众注意力 | 全在视频内容上，弹幕是叠加的情绪层 | 老师要对着**同一块屏幕**讲课，弹幕直接与讲课内容争抢注意力 |
| 内容可回看 | 能暂停、能关弹幕、能重看 | 一次性的，错过就没了 |
| 弹幕的信息价值 | 极低也没关系（「哈哈哈」「233」「前方高能」） | 低价值弹幕 = 纯噪音，会淹没有效信号 |

B 站弹幕里绝大多数是**情绪表达**而非**信息**，它的作用是让观众感到「有很多人跟我一起在看」。这个价值平移到课堂里，叫**破冰**——让不敢举手的学生第一次有了发声渠道。这是真实价值，但它**有保质期**，新鲜感大约 2~3 周。

**设计结论：** 「全屏飘过」保留。至于它是**全程常驻**还是**只在互动时刻出现**，有两种立场：

- **建议**：定位为互动模式，正常讲课时收成侧边条带，不遮挡课件
- **用户已拍板（D-003）**：**全程常驻、氛围最强** —— 宁愿接受课件被压着，也要那口气氛

按 D-003 执行。因此**「一键清屏 / 暂停」不是可选功能，而是这个模式能成立的唯一保险**：

> 清屏和暂停必须零延迟、零确认弹窗、单手可点（§7.3）。第一次出现刷屏而老师来不及制止，他就再也不会开第二次了。

**这个决定有一个必须承认的代价**：PPT 上会一直有文字飞过，后排学生看课件会更吃力。因此**密度、透明度、字号必须做成老师可调**（§8.1），默认值取保守档。**V1 上完一节课后应当重新审视这个决定** —— 它属于「只有真实课堂效果才能判断」的那一类。

### 2.2 老师是唯一的信息瓶颈

一个 90 人的班级，一节课产生 200 条弹幕是常态。老师**读不完**，这是物理限制。

由此推出本产品的第一性命题：

> **学生发的弹幕如果没有被回应，他第二次就不会再发了。**

反馈闭环不闭合，弹幕墙就只是个会动的装饰品。所以产品的重心**不是「怎么把弹幕飘出来」，而是「怎么让老师在一秒内看到最重要的 5 条」**。

三个解决机制：

1. **聚合计数** —— 学生不是发一条「没听懂」，而是点一个「没听懂」按钮；屏幕上那一条显示为 `没听懂 ×23`。学生看到自己的参与产生了可见效果，老师一眼看到重点。它比让 23 个人刷 23 条重复弹幕强一个量级，而且**天然抗刷屏**。
2. **点赞顶上来** —— 让好问题冒头。注意：点赞排序（要「固定」）和实时滚动（要「流动」）本质冲突，所以不能把高赞弹幕直接扔回弹幕流，必须给它**独立的展示位**。
3. **待回应问题池** —— 老师需要一块比弹幕墙更小的面板，只放「需要我回应的东西」。

### 2.3 匿名与秩序

这是最影响产品气质的决定。

| 方案 | 效果 | 代价 |
|---|---|---|
| 完全匿名 | 活跃度最高 | 一条不当言论就能让整门课被叫停，老师**没有任何反制手段** |
| 完全实名 | 秩序最好 | 学生不敢问「这么简单都不会」的问题，而**恰恰是这些问题最有价值**，活跃度大幅下降 |
| **对同学匿名 + 对老师可追溯** | 兼顾 | 需要一套身份采集流程（见 §8.6） |

**已采纳：对同学匿名、对老师可追溯。**

机制上等同于「匿名评教但教务后台留痕」：威慑力存在，学生的心理负担消失。学生知道自己说什么老师最终能看到，但不知道具体哪条被谁看到——**这个「知道」本身就是秩序的来源**。

### 2.4 弹幕与课件争夺同一块屏幕 ⚠️

教室投影是**整屏镜像**（复制模式），这带来一个无法用 UI 技巧绕开的事实：

> 弹幕墙和课件是**互斥**的 —— 除非弹幕不是画在自己那个窗口里，而是**浮在课件之上**。

而老师不可能在讲课时反复 `Alt+Tab`——每次切窗，全班都看得见；而且切走的那几十秒里弹幕全丢了。

**这不是细节，它决定产品形态。** 四条出路：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 窗口切换** | 弹幕墙做成独立页面，老师手动切 | 零开发成本 | 弹幕断续；切窗动作全班可见；老师要频繁操作 |
| **B 悬浮弹幕层** ✅ **已选** | 透明置顶、鼠标可穿透的浮窗，浮在 PPT 之上 | **唯一能同时做到「PPT 全屏」+「弹幕全屏飘过」的方案**，且不要求老师改变任何上课习惯 | 必须在教室电脑上运行一个程序，而这台电脑的权限与软件环境不可控 —— 解法见 §10.3 的 U 盘方案 |
| **C 课件托管** | 老师提前上传课件，系统全屏播放课件并叠加弹幕 | 零安装；顺带支持学生端同步看课件 | 老师多一步上传操作；复杂动画课件转换会失真；**且教室外网不可依赖**（课件传不进去） |
| **D 浏览器画中画** | 用 Chrome 的 Document PiP 把弹幕放进置顶小窗 | 零安装，无需 U 盘 | 窗口尺寸受限、浏览器版本要求未查证；仅作备选 |

**路线 C 的额外增值**（值得单独强调）：弹幕可以绑定到**具体哪一页课件**，老师能看到「第 12 页有 23 条没听懂」——这是精准到知识点的教学反馈，比一堆散弹幕有用一个量级。课后导出也变成「每页课件 + 该页的学生反馈」。**这个增值在路线 B 下拿不到**（悬浮层不知道 PPT 翻到了第几页），记录在此以备将来重新评估。

> **已由用户拍板选定路线 B。** 选它的理由不是妥协最少，而是它是**唯一不要求老师改变上课习惯的方案**：PPT 照常全屏放映，弹幕自己浮在上面。代价是把复杂度全部推给了「怎么在教室电脑上把程序跑起来」——而这台电脑是公用机器，外网每次上课还要手动登录。这个代价在 §10.3 集中处理。

## 3. 目标用户与使用场景

### 3.1 角色

| 角色 | 说明 | 使用设备 |
|---|---|---|
| **主讲老师** | 核心用户。控制课堂、查看反馈、回应问题 | **自己的手机**（控制台）+ 教室电脑（只负责投影） |
| **学生** | 主要参与者。发弹幕、点赞、看回应 | 自己的手机 |
| **助教**（暂不支持） | 后续可承担问题池的初筛 | — |

> 产品成败的判据是**老师**：他愿不愿意在第二节课继续打开它。学生的新鲜感会衰减，但老师只要觉得「有用」，这件事就能持续。

### 3.2 典型场景

一节 90 分钟的大学专业课，阶梯教室，80 名学生。老师**不带电脑**、带一个 U 盘；教室电脑**处于教室局域网内，外网需每次上课手动登录认证**；投影为整屏镜像。

- **00:00** 老师把 U 盘插进教室电脑，双击启动；弹幕层自动铺满整块屏幕，**透明、置顶、鼠标可穿透**
- **00:01** 屏幕右下角出现二维码（局域网地址）。学生手机连教室 WiFi，扫码进入，填写身份（仅老师可见）+ 昵称
- **00:05** 老师打开 PPT，正常全屏放映讲课。**弹幕从第一分钟起就全程飘在课件之上**，氛围从一开始就是满的
- **00:25** 讲到难点，学生开始刷 `这里没听懂`；老师手机震动——`这里没听懂 ×31` 达到阈值进入待回应池
- **00:28** 老师手机点「清屏」，投影上的弹幕瞬间清空，把课件完整让出来讲 30 秒，然后弹幕继续
- **00:80** 老师打开问题池，把三条高赞问题置顶回应——置顶条固定显示在屏幕顶部，不参与滚动
- **00:90** 下课，老师手机点「导出」，U 盘里落下本节课的弹幕记录；拔盘走人（教室电脑不留任何残留）

**这段场景暴露的关键约束**：

1. 老师全程**低头看手机** —— 必须在 §7.3 专门设计（提醒器模式）
2. **弹幕全程压在课件上**，遮挡是真实的 —— 密度/透明度/字号必须可调，且「一键清屏」不是可选项而是标配
3. **老师忘记带 U 盘 = 整节课产品不可用** —— 这是本方案最脆弱的一环，见 §13

## 4. 设计原则

1. **老师的控制权 > 学生的表达自由。** 清屏、暂停、删除都必须一步到位，不允许出现确认弹窗拖慢反应速度。
2. **默认热闹，但老师必须能一键安静。** 全屏弹幕**全程常驻**（用户已拍板，氛围优先）；因此「清屏」「暂停」「静音 5 分钟」必须零延迟、零确认、单手可点 —— 它们是这个模式能成立的**唯一保险**。
3. **反馈必须闭环。** 任何一条被聚合或被点赞的弹幕，学生端都要能看见「我的声音起作用了」。
4. **零安装、零注册。** 扫码即用，不装 App、不登录、不填表单超过一层。**这条现在也适用于老师**：教室电脑上不能要求安装任何东西，程序只能从 U 盘绿色运行。
5. **身份信息永不上投影。** 投影是全班共享的，任何能追溯到具体学生的信息都只能出现在老师的手机上。
6. **不能假设有网络出口。** 教室电脑的外网**每次上课都要手动登录一次**，随时可能断或过期，因此不可作为系统依赖：所有前端资源必须本地内置、屏蔽词库必须本地内置、地址必须用局域网 IP（D-013）。任何一行指向 CDN 的引用都会导致白屏。

| **Q-011** | **教室电脑的硬件与安全策略** | 能否从 U 盘运行 exe / 有无无线网卡 / 显卡性能 | 🟡 **风险已下降**（用户实测：管得松、无还原卡），但「能否从 U 盘跑 exe」仍须现场验证一次 |
| **Q-012** | **要不要改成老师自带笔记本电脑** | 自带笔记本 / 坚持 U 盘方案 | ✅ **维持 U 盘方案**（D-016）：老师能带但嫌麻烦，且教室电脑条件比预期宽松 |
| **Q-013** | **要不要加一条「公网中继」通道** | 纯局域网 / 局域网 + 公网中继 | 🔴 **新增，未决定**。用户实测「外网能上，只是要手动登录」打开了这条路，见 §10.5 |

### 关于 Q-010 的说明（最高优先级：学生怎么连上教室电脑）

「教室电脑处于教室局域网内、外网需每次上课手动登录」—— 这句话里**「教室局域网」是整个方案的生死线**，因为服务端现在就跑在这台电脑上：

| 学生手机连的是什么 | 能否访问教室电脑 | 说明 |
|---|---|---|
| 教室自己的无线路由器（电脑与手机同网段） | ✅ 通 | 最理想，不少教室就是这个配置 |
| 校园统一 WiFi，而电脑插网线 | ⚠️ **很可能不通** | 无线与有线常在不同子网，这是 AP 隔离的变体（§10.2） |
| 学生不连 WiFi，走自己的 4G | ❌ **完全不通** | 内网地址外网不可达 |
| 教室电脑开「移动热点」，学生连它 | ✅ 通 | 兜底方案，要求电脑有无线网卡且权限允许 |

**必须实地确认**：教室里有没有一个独立的无线路由器？学生平时连的是哪个 WiFi？连上之后能不能访问到教室电脑的地址？**这一项的优先级高于一切开发工作**，因为它不是代码能解决的问题。

### 关于 Q-011 的说明（U 盘方案能不能跑起来）

| 要确认的事 | 为什么重要 |
|---|---|
| 有没有可用的 USB 口 | 有些讲台机箱锁在柜子里，或者正面 USB 口是坏的 |
| **能否从 U 盘直接运行 `.exe`** | 部分学校组策略禁止从可移动驱动器执行程序 —— **这是本方案唯一的死穴** |
| 有无无线网卡 | 决定「教室电脑开热点」这条兜底路线是否可用 |
| 显卡与 CPU | 透明置顶窗口 + 60fps Canvas 的合成开销比普通窗口大，低端机会掉帧 |
| Windows 与 PowerPoint 版本 | 决定窗口置顶层级与透明 API 是否可靠 |
| 有无还原卡 / 管理员权限 | 用户实测：**没有还原卡、电脑管得松**，风险已下降。但「能否从 U 盘直接运行 exe」仍须现场验证一次 |

### 关于 Q-003 的说明（用户倾向「只做自由打字」，此处保留异议）

学生的实际输入成本对比：

- 自由打字：掏出手机 → 解锁 → 打开浏览器 → 聚焦输入框 → 打字 → 发送，**平均 15 秒**
- 预置按钮：掏出手机 → 点一下，**不到 1 秒**

差距是数量级的。更关键的是，**「聚合计数」机制完全依赖预置按钮**——没有按钮，就无法把 23 个人的意见合并成 `×23`，而只能得到 23 条重复弹幕，老师的瓶颈问题会更严重。

> 该决策标记为**待验证**。建议在 V0 原型阶段做一个 A/B 对照：同一批人，分别用「只有输入框」和「输入框 + 4 个快捷按钮」各发一轮，对比参与人数。用数据决定，不用直觉。

### 关于 Q-008 的遗留项

原 Q-008 是「去教室确认一堆事」的打包清单，现已拆解：**外网（需每次手动登录认证）、无还原卡、电脑管得松三项已由用户确认**，其余拆到 Q-010（局域网可达性）与 Q-011（硬件与策略）。仅剩一项留在原处：

| 要确认的事 | 为什么重要 |
|---|---|
| 投影是复制模式还是扩展模式 | 若是扩展模式，老师端可以放在讲台那块屏上，不必全程低头看手机（能部分缓解 Q-009 之外的最大体验痛点） |

## 7. 功能设计

### 7.1 页面与角色划分

| 载体 | 页面 | 使用者 | 说明 |
|---|---|---|---|
| **弹幕层窗口**（U 盘程序的主窗口） | 悬浮弹幕层 | 投影 | **透明、置顶、鼠标可穿透**。不再由老师手动开浏览器 —— 它就是那个 U 盘程序。**绝不出现任何身份信息** |
| `/host` | 老师控制台（**手机端优先设计**） | 老师手机 | 问题池 + 全局控制。**绝不上投影** |
| `/m` | 学生端 | 学生手机 | 扫码进入 |
| `/screen` | 纯网页版弹幕墙（**降级备用**） | 投影（兜底） | 当 U 盘方案在某个教室跑不起来时，用教室电脑浏览器打开它，退化为「全屏弹幕墙 + 手动切课件」 |

> 投影上的内容（弹幕层窗口）与老师手机上的内容（`/host`）是**同一个班的两条独立视图流，服务端按角色分流广播**（D-009）。
>
> **`/screen` 在新方案下不再是主路径**，但必须保留：它是 U 盘被组策略拦住、或透明窗口在低端机上不可靠时**唯一还能用的退路**（见 §13）。

### 7.2 学生端

**加入流程**（唯一一次表单，不超过一层）：

```
扫码 → 填写身份（学号 + 姓名，仅老师可见）
     → 填写昵称（可留空 = 「匿名同学」）
     → 进入
```

**主界面**：

- 顶部：当前课堂状态（「弹幕已暂停」/「进行中」）
- 中部：自己发过的弹幕及其实时状态（被点赞数、是否被老师置顶/回应）
- 底部：输入框 + 发送按钮（+ 快捷按钮，取决于 Q-003）
- 冷却中：发送按钮显示倒计时，避免无效点击

**关键交互**：发送后**本地先回显**，不等服务端确认，让手感即时；服务端确认失败（被限流/被拦截）时再撤销并给出原因。

### 7.3 老师端（`/host`，手机端）

**要正视的问题**：老师一边讲课一边低头看手机，观感差且分心。所以手机端**不能做成一个完整控制台**，定位应该是：

> **默认是「提醒器」，需要时才展开成「控制台」。**

**形态一：提醒器（默认，90% 的时间）**

- 一个大徽章：`3 个待回应`
- 达到阈值时**震动**提醒（`没听懂 ×31` 冲进问题池）
- 不做任何其他 UI，老师不用看它

**形态二：控制台（点开后）**

```
┌─────────────────────────┐
│ 待回应                  │
│ ▸ 这里没听懂 ×31        │
│   👍12  [置顶] [已回应] │
│ ▸ 能举个例子吗 ×8       │
│   👍7   [置顶] [已回应] │
├─────────────────────────┤
│  [ 清屏 ]   [ 暂停 ]    │   ← 大按钮，单手可点
│  [ 静音5分钟 ] [ 置顶 ]  │   ← 全程常驻，「清屏」是最高频动作
├─────────────────────────┤
│ 在线 78 · 弹幕 213 · 41人│
│ ⚙ 屏蔽词 / 导出 / 设置   │   ← 折叠到二级页
└─────────────────────────┘
```

**手机端设计约束**：

- 只保留 4 个高频动作做成大按钮（清屏 / 暂停 / 静音5分钟 / 置顶），其余折叠
- 「清屏」和「暂停」**不做二次确认**，一次点击立即生效 —— 全程常驻模式下它们是老师把课件抢回来的唯一手段
- 删除操作支持**左滑**，不做二次确认弹窗
- 所有操作必须在投影上 1 秒内生效
- 竖屏单手可操作，按钮最小高度 44px

**老师专属信息（只在这里出现）**：每条弹幕可展开查看发送者学号姓名，用于追溯；问题池支持「拉黑该设备」。

### 7.4 悬浮弹幕层（主视觉，投影上的全部内容）

- 一个**透明、无边框、置顶、鼠标可穿透**的窗口，铺满整块屏幕
- 老师正常在它下面全屏放映 PPT，弹幕飘在 PPT 之上 —— **这是路线 B 的全部价值**
- Canvas 渲染，**全程常驻**（用户已拍板），从上课第一分钟飘到下课
- **置顶弹幕固定显示在顶部**，不参与滚动；被老师回应的弹幕加高亮描边
- 右下角常驻二维码（局域网地址），方便迟到学生扫码进入
- **鼠标穿透**：弹幕层不接收任何鼠标事件，老师的点击全部落到 PPT 上；老师的一切操作走手机端
- **安全红线：任何能追溯到具体学生的信息都不得出现在此窗口**

**三个必须实测、不能靠推理确认的技术点**（见 §12 的 V-1 验收项）：

1. 窗口能否盖住 **PowerPoint 放映模式** —— 若 PPT 走的是独占全屏（DirectX exclusive fullscreen），置顶窗口会被压下去，整个方案失效
2. 鼠标穿透在 Windows 上是否稳定（Electron `setIgnoreMouseEvents(true, { forward: true })`）
3. 透明窗口 + 60fps Canvas 在教室电脑上的**实际帧率**（透明合成比普通窗口贵得多）

**兜底的视觉方案**：若透明合成在教室电脑上不可靠（黑底 / 掉帧 / 穿透失效），降级为**不透明底部条带** —— 屏幕底部 25% 是实心弹幕带，上方 75% 留给窗口化的 PPT。这等于退回到「路线 A」，但至少能用，且视觉效果仍然像一条真正的弹幕带。

## 8. 关键机制设计

### 8.1 弹幕渲染与轨道分配

Canvas 单画布，一帧一绘制。核心是把屏幕纵向切成 N 条**轨道（lane）**，新弹幕要找到一条不会追尾的轨道：

```
屏幕高度 H，弹幕行高 h → 轨道数 N = floor(H / h)

新弹幕到达时，按顺序尝试轨道 i = 0..N-1：
  若轨道 i 为空 → 占用
  否则检查该轨道最后一条弹幕 t：
    若 t 的右边缘 + 安全间距 < 屏幕右边界（即 t 已完全进入屏幕）
      且 新弹幕到达左边界所需时间 < t 移出右边界所需时间（不会被追上）
      → 占用轨道 i
  所有轨道都不满足 → 进入等待队列

速度策略：速度与弹幕长度正相关（长弹幕快一些），保证同屏停留时间一致
```

需要调优的手感参数（**全部做成老师端可调滑块**）：滚动速度、字号、透明度、同屏最大密度。

> 手感是这个产品最容易被低估的环节。飘得太快看不懂、太慢会积压；字号太大挡课件、太小后排看不见；透明度不够显脏、太高看不清。**这些参数只能在真实投影上反复调**，所以 V0 阶段就要把它们做成可调项，投入回报率极高。

### 8.2 聚合计数

在时间窗口（建议 30 秒）内，把语义相同的预置弹幕合并为同一条，计数累加：

- `没听懂 ×23` —— 学生点击后，屏幕上已存在的那条数字实时 +1，并有一个轻微放大的动效
- 窗口过期后，该条固定下来，不再增长

> 这是 **Q-003 依赖预置按钮**的根本原因：没有预置语义，就没有聚合的锚点。

### 8.3 点赞与热点

- 每个设备对同一条弹幕只能点一次赞（设备级去重）
- 点赞数不直接改变弹幕在流中的位置（会与滚动逻辑冲突），而是提升它在**问题池**中的排序
- 点赞数达到阈值时，弹幕墙顶部出现一条不滚动的「热点」提示

### 8.4 限流与防刷屏

服务端令牌桶，设备维度：

| 规则 | 阈值 |
|---|---|
| 发送间隔 | ≥ 3 秒 |
| 每分钟上限 | 10 条 |
| 单节课上限 | 200 条 |
| 连续触发限流 | 自动静默 60 秒，并提示学生 |

限流提示必须是**友好**的（「说得太快啦，3 秒后再来」），不是报错，否则学生会以为程序坏了。

### 8.5 内容安全

三层防护，按实际有效性排序：

1. **服务端限流**（§8.4）—— 最有效，直接掐断刷屏
2. **服务端屏蔽词** —— 命中即拦截，并对该设备计数。词库**必须本地内置**，不能调用任何云端内容审核 API（外网不可依赖，D-013）
3. **老师一键撤回 + 拉黑设备** —— 兜底。屏蔽词永远做不全，真正的兜底是老师的手速

> 屏蔽词库不追求完备。真实课堂上，起决定作用的是「老师能在 2 秒内把那条删掉」。

### 8.6 身份与追溯机制

**问题**：如果学生完全匿名进入，老师端能看到的只有设备指纹（localStorage），而设备无法对应到具体的人——「可追溯」就名存实亡。

**方案**：首次进入时**必须填学号 + 姓名**，但：

- 学生之间看到的一律是「匿名同学」（或自取昵称）
- 只有老师端能展开查看真实身份
- 学生端**明确告知**「老师可以看到你是谁」

这个「告知」不是妥协，而是**有意为之的威慑设计**：学生知道自己说的话老师最终能看到，但不知道具体哪条会被翻出来——这正是秩序的来源，与匿名评教机制同构。

> **D-009 让这个机制变得更干净了**：老师端在手机上，身份信息天然不可能出现在投影上。若老师端在教室电脑屏幕上，则每次查看身份都要担心投屏泄露。

## 9. 技术架构

> 本章只给出架构与协议的**结论**。实现路径、算法细节、目录结构、打包与测试策略见 [产品技术方案](产品技术方案.md)；两份文档冲突时以本文档的决策为准。

### 9.1 架构

```
        U 盘（老师随身携带，D-012）
   ┌────────────────────────────────────────┐
   │  单个免安装程序（Electron）              │
   │   ├ 主进程：Node HTTP + WebSocket 服务   │
   │   │   ├ 静态页面托管 (/host /m /screen)  │
   │   │   ├ 广播器（按角色分流）             │
   │   │   ├ 限流器（设备级令牌桶）           │
   │   │   ├ 屏蔽词过滤（本地内置词库）       │
   │   │   └ 聚合器（时间窗合并计数）         │
   │   ├ 渲染窗口：透明 · 置顶 · 鼠标穿透     │
   │   └ 存储：内存态 + 定时落盘到 U 盘       │
   └────────────────────────────────────────┘
                    ↑ 插进教室电脑双击运行
                      （不安装、不写 C 盘）
   ┌────────────────────────────────────────┐
   │ 教室电脑（教室局域网内；外网需手动登录）  │
   │   ├ 弹幕层窗口  ──→ 投影（全班可见）     │
   │   └ 服务端 :3000 （本机）                │
   └────────────────────────────────────────┘
                    │  http://192.168.x.x:3000
          ┌─────────┴─────────┐
     老师手机 /host        学生手机 /m ×N
     （控制台·私有）       （发弹幕）
```

**两条视图流的隔离是这个架构的关键**：

| 流 | 内容 | 可见范围 |
|---|---|---|
| 弹幕层窗口 | 弹幕内容、聚合计数、置顶状态 | 全班 |
| `/host` 流 | 上述全部 **+ 身份信息 + 问题池 + 控制状态** | 仅老师 |

服务端按连接角色分流广播，**身份信息永远不会进入弹幕层**——这是服务端的责任，不能只靠前端不渲染。

> ⚠️ **这张图里每一处「局域网」都依赖 Q-010 的实地确认。** 如果学生手机所在的 WiFi 与教室电脑不在同一子网，`192.168.x.x` 根本不可达，整个方案不成立。这是当前项目的**最大单点风险**，且无法用代码绕过。

### 9.2 选型

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | **Electron**（内含 Node.js） | **一个程序同时解决「透明置顶窗口」和「本地服务端」两件事**；老师不需要在教室电脑上装 Node（D-012） |
| 分发形态 | 免安装绿色版，解压/双击即用 | 教室电脑是公用机器、无管理员权限，不能走安装流程（D-010） |
| 通信 | `socket.io` | 手机在教室切后台/信号抖动是常态，自带重连与房间 |
| 渲染 | 原生 Canvas 2D | 无框架开销，60fps 可控 |
| 前端框架 | **不用**（原生 JS），且**所有资源本地内置** | 教室外网不可依赖，任何一个 CDN 外链都会在断网时直接白屏（D-013） |
| 存储 | 内存 + JSON 落盘到 **U 盘** | 单节课数据量极小（≤500 条 × ~100B ≈ 50KB）；落 U 盘可带走本课全部数据（D-015） |
| 二维码 | 主进程本地生成 | 内容是本机局域网 IP（`http://192.168.x.x:3000`），不是域名 |
| 托管 | **无** —— 服务就跑在教室电脑上 | 见 D-011。本项目**没有持续性成本**，原先估算的云服务器 ¥100/年 不再需要 |
| HTTPS / 域名 | **不需要** | 内网 IP，证书无意义；纯 HTTP |

> **选型里唯一新增的技术风险是 Electron 本身**：打包体积约 150MB（放 U 盘无所谓），但从 U 盘冷启动可能偏慢。**「双击到弹幕出现在屏幕上」必须控制在 10 秒内**，否则每次上课都会让老师烦躁。

### 9.3 WebSocket 事件协议（草案）

| 方向 | 事件 | 载荷 | 说明 |
|---|---|---|---|
| C→S | `join` | `{ role, classId, identity?, nickname }` | 学生/老师/大屏加入 |
| C→S | `danmaku:send` | `{ text }` | 发弹幕 |
| C→S | `danmaku:like` | `{ id }` | 点赞 |
| S→C | `joined` | `{ deviceId, myHistory[] }` | 加入成功，回带历史 |
| S→C | `danmaku:new` | `{ id, text, nickname, color, ts }` | 新弹幕广播 |
| S→C | `danmaku:update` | `{ id, likes?, aggregate? }` | 计数变更 |
| S→C | `danmaku:remove` | `{ id, reason }` | 删除（老师撤回/屏蔽词） |
| S→C | `danmaku:pin` | `{ id, pinned }` | 置顶 |
| S→C | `state` | `{ paused, mode, online }` | 课堂状态同步（重连后必发） |
| S→C | `host:alert` | `{ id, reason, aggregate }` | **仅发给老师**：有新问题进入待回应池，触发手机震动 |
| C→S | `host:*` | — | 老师控制指令（清屏/暂停/删除/拉黑） |

> **重连后必须全量同步状态**，否则学生手机会停留在旧状态（比如老师已经清屏了，学生端还显示着旧弹幕）。老师手机锁屏后重开也属于这一类。

## 10. 教室环境约束与网络

### 10.1 教室硬件与软件约束（来自真实使用环境）⚠️

四条硬约束（**后三条均为用户实地确认**）：

1. **投影是整屏镜像**（复制模式），投影上显示什么，学生就看到什么 —— 老师端不能上屏
2. **老师不带自己的电脑**，使用教室公用电脑 —— 用户实测：**「嫌麻烦，真要带也能带」**，所以这是**主动选择**而非能力限制（见 §10.4 与 D-016）
3. **教室电脑是公用机器，软件环境不受自己控制** —— 无管理员权限、装着各种校园管控软件。**用户实测：这台电脑没有还原卡、管得比较松**，风险比预期低，但仍不能当成保证
4. **教室电脑的外网需要手动认证** —— 用学生账号登录校园网才能上网，**每次上课都要登一次**。这意味着外网**不能作为系统依赖**：认证过期、中途掉线、换账号，都会让服务当场失联

由此推出四个结论：

| 结论 | 依据 |
|---|---|
| 老师端载体 = 老师自己的手机（D-009） | 约束 1 |
| 教室电脑**不安装任何程序**，一切从 U 盘绿色运行（D-010 / D-012） | 约束 3。既然服务必须跑在这台机器上，「零安装」就只剩下「不写 C 盘、不点下一步」这一种实现方式 |
| **服务只能跑在教室电脑本机**（D-011） | 约束 2 + 约束 4：老师选择不带电脑，而外网每次要手动认证、不可依赖，教室电脑是唯一的选择 |
| **公网托管不成立** | 约束 4。注意措辞：**不是「连不上」，而是「随时可能断，断了必须人工重新登录」** |

> ### ⚠️ 这一条推翻了本文档上一版的结论
>
> 上一版建议「服务放到公网，教室电脑退化为纯浏览器终端」，理由是它同时满足零安装、绕过 AP 隔离、老师端不上屏、还原卡无关四条。**约束 4 把这条路堵死了**：一节课 90 分钟里只要认证过期一次，弹幕服务就整体失联，而老师正站在讲台上，不可能停下来重新登录校园网。
>
> 代价是：
>
> - **可达性问题重新变成首要风险**（§10.2），而且**没有公网这个逃生门**
> - 前端不能引用任何 CDN（D-013），否则断网即白屏
> - 老师多了一个必须记住的动作：**带 U 盘**（忘了 = 整节课不可用）
> - 「路线 C 课件托管」（§2.4）也一起失效 —— 课件没有可靠通道传进教室电脑
>
> 换来的好处：**零持续性成本、数据不出校园、外网断了也不影响**（只要局域网通）。
>
> **补充（用户后续确认）**：约束 4 的实际严重程度比上一版假设的轻 —— 外网**是能上的**，只是要人工登录一次。这不足以让公网托管复活（不可依赖），但**足以开辟一条混合路线**，见 §10.5（Q-013）。

### 10.2 可达性：本方案最大的单点风险 ⚠️

**这是本项目最容易翻车、且开发阶段完全发现不了的地方。**

服务端跑在教室电脑的 `192.168.x.x:3000` 上，学生手机必须能访问到这个**内网地址**。但：

- 学校 / 公共 WiFi 的 AP 经常开启**客户端隔离（AP Isolation）**，同一 WiFi 下的设备之间无法互相访问
- 即便没有 AP 隔离，**无线网段与有线网段经常是隔离的**：教室电脑插网线，学生手机连校园 WiFi，两者根本不在一个子网
- 学生若用自己的 4G 流量，内网地址**完全不可达**

表现是：

> 你在自己电脑上开两个浏览器窗口测试，一切正常；到了教室，学生手机根本连不上老师的电脑。

| 方案 | 到达率 | 代价 |
|---|---|---|
| 学生连**教室自己的无线路由器**（与电脑同网段） | ✅ 高 | 取决于教室是否真有这么个路由器 —— **Q-010** |
| 教室电脑开「移动热点」，学生连它 | ✅ 高 | 需无线网卡 + 权限；学生要断开自己的网络 |
| 学生连校园 WiFi → 访问教室电脑 | ⚠️ **可能完全不通** | 无 |
| ~~服务部署到公网服务器~~ | ~~100%~~ | ❌ 外网随时可能断，断了还得人工重新登录校园网（约束 4）——**它的改良版见 §10.5** |
| ~~内网穿透~~ | ~~高~~ | ❌ 同样依赖一条稳定的外网连接，且要求服务一直挂着，不可靠 |

**这是物理约束，不是工程问题**，只能靠现场确认 + 兜底预案。因此 **Q-010 的优先级高于一切开发工作**。

### 10.3 结论：U 盘承载一切（D-012）

所有约束合起来只剩一条路：**老师带一个 U 盘，里面装着完整的系统，插进教室电脑双击即用。**

U 盘里装的是**一个程序**，它同时是两样东西：

- **服务端** —— 主进程内嵌 Node HTTP + WebSocket，教室电脑上不需要预先装 Node
- **弹幕层** —— 渲染进程画那个透明置顶、鼠标穿透的全屏窗口

这样老师只需要记住**一个动作**（插 U 盘、双击），而不是三个（装 Node、开服务、开浏览器）。这一点在真实课堂里是决定性的：任何需要老师「先做 A 再做 B 再做 C」的方案，第三周就会被放弃。

**落地要点**：

| 要点 | 说明 |
|---|---|
| 免安装 | 解压即用的绿色版；不写 C 盘，数据落 U 盘（D-015），教室电脑上不留任何痕迹 |
| 端口 | 固定一个不常用的端口（如 3000），避免和教室电脑上别的服务打架 |
| **防火墙** | 首次运行 Windows 会弹防火墙授权框。**若教室电脑没有管理员权限，可能无法放行局域网访问** —— 这是上线前必须实测的一环 |
| 杀软 | 部分校园杀软会拦截可移动介质上的 exe，需提前跟学校确认能否加白名单 |
| 启动速度 | 从双击到弹幕出现在屏幕上 **必须 < 10 秒**（Electron 冷启动 + 透明窗口创建都要时间） |
| 数据落盘 | 弹幕记录写在 U 盘里，下课拔盘就等于带走了这节课的全部数据 |
| 拒绝残留 | 退出时不写注册表、不留后台服务，教室电脑上「来过跟没来过一样」 |

### 10.4 已评估并否决的替代路线：老师自带笔记本（Q-012 → D-016）

U 盘方案的全部复杂度，都来自「必须在一台自己不能控制的电脑上运行程序」。如果老师**愿意并且能够**自带笔记本，这些复杂度会一次性消失：

| 问题 | U 盘方案 | 自带笔记本 |
|---|---|---|
| 组策略/杀软拦截外置程序 | 🟡 用户实测管得松，风险已下降 | ✅ 无（自己的电脑自己说了算） |
| 防火墙放行 | 🔴 可能无权限 | ✅ 有管理员权限 |
| 公用机器重置 | 🟡 靠不写 C 盘规避（实测已无还原卡） | ✅ 无关 |
| 透明置顶窗口可靠性 | 🟡 未知硬件 | ✅ 可提前在自己机器上验证 |
| 服务的可达性（Q-010） | 🔴 依赖教室网络 | 🟡 同样依赖，但可以用自己的热点兜底 |
| 老师要带的设备 | 一个 U 盘 | 一台笔记本（重得多） |

**唯一的阻塞项是**：老师的笔记本能不能接上教室的投影（HDMI / Type-C / VGA 接口是否匹配、讲台有没有留线、切换信号源是否方便）。

> **✅ 结论（用户已拍板，D-016）：维持 U 盘方案，不带笔记本。**
> 理由是老师「嫌麻烦，真要带也能带」—— 这是**主动选择**，不是能力限制；而用户同时确认了教室电脑管得松、没有还原卡，U 盘方案的可行性比预期高。因此这条路**记录在此备查**：如果 V-1 实测发现「从 U 盘运行 exe」被拦住，它就是第一顺位的退路。

### 10.5 新增待议路线：公网中继（Q-013）🔴

**这条路的由来**：上一版把约束 4 写成「教室电脑完全不能联网」，因此公网托管被一票否决。用户随后澄清：**外网其实是通的，只是每次上课要用学生账号登录一次认证。**

这个差别很关键 —— 它不足以让「教室电脑退化为纯浏览器终端」复活（浏览器浮层盖不住 PPT 放映，§2.4），**但足以开辟一种混合架构**：

| | 纯局域网方案（当前，D-011） | 公网中继方案（Q-013） |
|---|---|---|
| 服务端位置 | 教室电脑本机 `:3000` | 公网云服务器（约 ¥100/年） |
| 教室电脑上的程序 | 既是服务端又是弹幕层 | **只是客户端**：渲染透明浮层 + 主动连出到公网服务器 |
| 学生手机连的地址 | `http://192.168.x.x:3000`（局域网） | `https://弹幕.example.com`（公网） |
| **Q-010 可达性风险** | 🔴 最大风险，完全取决于教室网络 | ✅ **彻底消失**：学生用 4G、校园 WiFi 都行 |
| 防火墙 / AP 隔离 / 跨子网 | 🔴 全都要赌 | ✅ 全部无关（出站连接不需要任何入站权限） |
| 老师手机控制台 | 必须和教室电脑同网段 | ✅ 用 4G 也行 |
| 对教室外网的依赖 | ✅ 完全不依赖 | 🔴 **全程依赖**：认证一过期，弹幕当场停 |
| 数据 | 不出校园 | 🔴 出校园（匿名+可追溯，需评估合规） |
| 成本 | 0 | 约 ¥100/年 + 一个域名 + 证书 |
| V1 实现复杂度 | 低 | 中（多一套服务端部署 + 重连 + 双模式） |

**它解决的是本项目最大的风险（Q-010），换来的是一个新的依赖（外网不能断）。** 两者都是"整节课级"的失败模式，区别在于：教室网络不通是**你无法自救**的（只能换教室或放弃），而认证掉线是**老师可以重登一次**的。从这个角度看，公网中继的失败模式更可控。

**折中做法（可能是最优解）**：程序**同时**起本地服务并连接公网中继，二维码指向一个引导页 —— 学生点进去后自动选一条通的路径。这样教室网络通就用局域网（快、不出校园），不通就走公网。代价是 V1 要多写一层，**建议推迟到 V1 之后再评估**。

**待确认**：
- [ ] 校园网认证一次能维持多久？中途会不会强制重认证？
- [ ] 教室电脑能否长期保持认证状态（锁屏、休眠会不会断）？
- [ ] 学校是否允许这么做（数据出校园、外网服务器）？

## 11. 版本路线图

| 阶段 | 交付内容 | 验证的核心假设 |
|---|---|---|
| **V-1**（不写代码） | 带一台笔记本去教室，实测 U 盘程序能否运行、学生手机能否连上本机 IP、透明置顶窗口能否盖住 PPT 放映 | **整个方案是否成立**。这几件事全是物理约束，写再多代码也改不了 |
| **V0** | 单机原型：一个页面自己给自己发弹幕；滑杆可调速度/字号/透明度/密度 | 弹幕的**手感** —— 这是所有体验的基础 |
| **V1** | 真多端：学生扫码发、弹幕层飘、老师手机控；打包成 U 盘绿色版 | ① 老师从插 U 盘到能用是否够快 ② 手机控制链路是否顺手 ③ 端到端延迟 |
| **V2** | 老师管控：清屏、暂停、静音 5 分钟、删单条、屏蔽词、限流 | 老师愿不愿意开第二次 |
| **V3** | 互动：聚合计数、点赞、热点区、问题池、置顶、手机震动提醒 | 学生第 3 次课还发不发 |
| **V4** | 数据沉淀：课后导出弹幕记录（落 U 盘）、高频问题汇总 | 对老师有没有长期价值 |

**V-1 必须先做的理由**：现在有三个**物理层面**的未知（能不能从 U 盘运行、学生手机能不能连上、弹幕层能不能盖住 PPT）。任何一个不成立，产品形态就要换。**这三件事没有一行代码能解决，但半天就能测完。** 先测，再决定写什么。

**V0 紧接着做的理由**：手感参数无法靠推理确定，只能在真实投影上试。如果 V0 跳过、直接做完整功能，最后很可能发现「氛围对了，但没人看得清」——那时返工成本极高。

> **V0 不依赖 V-1 的结论，可以并行开工**（它就是本地一个页面加几个滑杆），这是当前唯一可以立刻动手的部分。

| **教室电脑无权限放行防火墙** | 学生连不上，且老师无法自救 | V-1 实测；必要时让学校 IT 预先加规则 |
| **低端教室电脑掉帧** | 透明合成 + Canvas 开销大，弹幕卡顿 | V0 就把密度/速度/透明度做成可调；避免阴影、模糊等昂贵合成效果 |
| **新鲜感衰减** | 第 3 周后无人发弹幕 | 让弹幕与课堂内容强绑定（老师提问 → 弹幕作答），而不是让弹幕孤立存在 |
| **老师不适应手机操作** | 老师觉得麻烦，第二节课不再打开 | 提醒器模式：默认不打扰，只在阈值触发时震动；高频动作做成大按钮 |
| **全程常驻导致课件被遮挡** | 影响正常讲课 | 一键清屏零确认；密度/透明度可调；默认透明度取保守值 |
| **老师低头看手机的观感** | 学生觉得老师不专心 | 提醒器模式把手机使用时长压到最低 |
| **学生用弹幕聊天** | 弹幕流变成闲聊区 | 限流 + 老师撤回 + 屏蔽词 |
| **手机电量/流量** | 学生不愿长时间开着 | WebSocket 心跳降到最低；页面极简 |
| **老师用别的电脑上课** | 换一台机器，U 盘方案同样要重测一遍 | 把 V-1 的实测做成**一张清单**，换教室就照着跑一遍 |
